# **Техническое задание DUAL TETRIS — фаза 1А и 1Б**

Зафиксированные решения

Для первой фазы принимаем следующие правила:

1. **Стартовая энергия — 0** по каждому из четырёх цветов.
2. **Энергия начисляется за все цветные кубики во всех уничтоженных линиях.** Не только за доминирующий цвет.
3. **Существующие автоматические эффекты временно сохраняются.** Начисление энергии и новая система способностей добавляются поверх текущей механики, не заменяя её.

Ниже ТЗ привязано к структуре и коду архива `dual-tetris-main.zip`. В архиве используется TypeScript, игровой движок находится в `packages/core`, сервер работает через WebSocket-библиотеку `ws`, а клиент отрисовывает игру через Canvas 2D. Это не проект на FastAPI или Socket.IO.

## **1. Текущая архитектура и точки интеграции**

В архиве уже есть подходящие места для расширения игры:

| Файл                            | Текущее назначение                                   | Изменения в первой фазе                                    |
| ------------------------------- | ---------------------------------------------------- | ---------------------------------------------------------- |
| `packages/core/src/engine.ts`   | Игровое состояние, очистка линий, эффекты, симуляция | Энергия, способности, активация и их эффекты               |
| `packages/core/src/protocol.ts` | WebSocket-сообщения, события, снимок состояния       | Новые команды, события и поля энергии                      |
| `packages/core/src/config.ts`   | Игровые параметры и настройки эффектов               | Лимиты энергии, стоимость и параметры способностей         |
| `apps/server/src/server.ts`     | Комнаты, WebSocket, игровой цикл                     | Проверка команд активации, отправка обновлённого состояния |
| `apps/web/src/main.ts`          | Canvas, обработка событий, клиентское состояние      | Отображение энергии, кнопки способностей, обратная связь   |
| `tests/core.test.ts`            | Тесты игрового ядра                                  | Тесты начисления энергии и способностей                    |
| `tests/integration.test.ts`     | Интеграционные тесты                                 | Проверка обмена командами и состояния по WebSocket         |

**Важная особенность текущего движка:** в `lockPiece()` уже собирается массив `colorCounts`. Однако после очистки линий он используется для выбора одного доминирующего цвета через `pickDominantColor()`. Это позволяет добавить начисление энергии в существующий алгоритм, не переписывая механизм очистки линий.

В коде используются такие идентификаторы цветов:

| ID | Цвет    | Энергетический резервуар  |
| -- | ------- | ------------------------- |
| 1  | Зелёный | Green                     |
| 2  | Синий   | Blue                      |
| 3  | Красный | Red                       |
| 4  | Жёлтый  | Yellow                    |
| 5  | Джокер  | Отдельного резервуара нет |

Кубики джокера с ID `5` не попадают ни в один из четырёх цветовых резервуаров. Доминирующий цвет, волны и существующие эффекты продолжают рассчитываться по старым правилам.

# **Фаза 1А. Система энергии**

Без изменения существующего баланса боя

## **2. Цель фазы 1А**

Добавить каждому игроку четыре независимых резервуара энергии:

- зелёный;
- синий;
- красный;
- жёлтый.

Энергия начисляется автоматически при уничтожении линий. На этом этапе игрок ещё не использует способности — фаза нужна для внедрения и проверки новой системы накопления.

## **3. Игровые правила энергии**

### **3.1. Начальное состояние**

При создании матча у каждого игрока:

```
energy: {
  green: 0,
  blue: 0,
  red: 0,
  yellow: 0
}
```

Энергия обнуляется при создании нового матча и не переносится из предыдущего.

### **3.2. Начисление энергии**

За каждый уничтоженный кубик начисляется одна единица энергии соответствующего цвета.

Пример: игрок уничтожил одну линию из 10 кубиков:

Пример распределения кубиков

# **+4**

Зелёная

# **+3**

Синяя

# **+2**

Красная

# **+1**

Жёлтая

Если уничтожено несколько линий одновременно, учитываются все кубики во всех этих линиях.

Например, при уничтожении двух линий из 10 кубиков каждая движок суммирует цветовые количества по обеим линиям и начисляет энергию по полученным итогам.

**Правило:** энергия не зависит от доминирующего цвета. Доминирующий цвет продолжает использоваться старой игровой механикой, а энергия рассчитывается отдельно.

### **3.3. Ограничение энергии**

Предусмотреть максимальное значение каждого резервуара через конфигурацию:

```
energyMax: 100
```

При начислении:

```
energy[color] = Math.min(
  energyMax,
  energy[color] + gained
);
```

Значение `100` — стартовый настраиваемый параметр баланса, а не ограничение архитектуры. Если резервуар заполнен, лишняя энергия не переносится и не конвертируется.

## **4. Изменения в игровом ядре**

### **4.1.&#x20;**`packages/core/src/engine.ts`

В `PlayerState` добавить поле:

```
export interface PlayerState {
  // Существующие поля...
  energy: {
    green: number;
    blue: number;
    red: number;
    yellow: number;
  };
}
```

В `createMatch()` инициализировать четыре значения нулями для обоих игроков.

В `lockPiece()` оставить текущий алгоритм:

1. Зафиксировать фигуру на поле.
2. Найти уничтоженные линии.
3. Подсчитать кубики каждого цвета.
4. Начислить энергию.
5. Выбрать доминирующий цвет старым методом.
6. Выполнить существующие эффекты.
7. Создать волну и продолжить текущий игровой процесс.

Начисление энергии должно происходить один раз на каждую фактическую очистку линий. Повторное начисление при создании снимка состояния недопустимо.

Рекомендуется вынести начисление в отдельную функцию:

```
function addEnergy(
  player: PlayerState,
  colorCounts: number[],
  energyMax: number
): void
```

Функция должна обрабатывать только цвета `1–4`.

### **4.2. Событие начисления энергии**

В `GameEvent` добавить событие:

```
| {
    type: 'energy_gain';
    player: 0 | 1;
    gained: {
      green: number;
      blue: number;
      red: number;
      yellow: number;
    };
    total: {
      green: number;
      blue: number;
      red: number;
      yellow: number;
    };
  }
```

Событие отправляется только тогда, когда уничтожена хотя бы одна линия. Поле `gained` показывает начисление за текущую очистку, `total` — новое состояние резервуаров.

### **4.3.&#x20;**`SnapshotMessage`

В `packages/core/src/protocol.ts` добавить энергию обоих игроков:

```
energy: [
  EnergyState,
  EnergyState
];
```

Где `EnergyState` — тип с четырьмя числовыми полями.

В `createSnapshot()` из `engine.ts` передавать актуальные значения энергии обоих игроков. При формировании снимка не изменять энергию.

### **4.4.&#x20;**`packages/core/src/config.ts`

Добавить параметр:

```
energyMax: 100
```

Он должен входить в `GameConfig` и `DEFAULT_CONFIG`.

## **5. Изменения интерфейса в фазе 1А**

В `apps/web/src/main.ts`:

- Отображать четыре цветовых индикатора энергии игрока.
- Показывать актуальные значения из `SnapshotMessage`.
- Обновлять индикаторы после получения нового снимка.
- При начислении энергии можно показывать короткую анимацию увеличения значения.
- Не добавлять пока кнопки активации способностей.

Энергия должна быть видна игроку во время матча, но не должна занимать значительную часть игрового поля.

## **6. Критерии приёмки фазы 1А**

- У обоих игроков энергия начинается с нуля.
- За уничтоженные линии учитываются кубики всех цветов.
- При очистке нескольких линий учитываются все уничтоженные кубики.
- Энергия начисляется в правильные цветовые резервуары.
- Джокеры не начисляют энергию.
- Ни один резервуар не превышает установленный максимум.
- Энергия не начисляется повторно при отправке снимков.
- Энергия обоих игроков передаётся через WebSocket.
- Интерфейс отображает актуальные значения.
- Старые эффекты лечения, заморозки, метеоритов и джокеров работают без изменений.
- Существующие комнаты, управление фигурами, волны, урон и переподключение продолжают работать.

**Результат фазы 1А:** у каждого игрока есть четыре работающих энергетических резервуара, которые наполняются в зависимости от цветов уничтоженных кубиков. Боевая механика пока не меняется.

# **Фаза 1Б. Система активируемых способностей**

Ручная активация игроком

## **7. Цель фазы 1Б**

Добавить возможность тратить накопленную энергию на специальные способности.

Игрок получает четыре слота способностей. Он сам выбирает, какие способности установить в слоты, и самостоятельно нажимает кнопку для активации.

Энергия общая для всех способностей одного цвета.

Например, если у игрока установлены две синие способности, обе используют один синий резервуар. Энергия не дублируется и не резервируется отдельно под каждый слот.

## **8. Правила способностей**

### **8.1. Четыре слота**

В состоянии игрока предусмотреть четыре слота:

```
type AbilitySlot = {
  abilityId: string | null;
};

type AbilitySlots = [
  AbilitySlot,
  AbilitySlot,
  AbilitySlot,
  AbilitySlot
];
```

На этапе 1Б слоты можно заполнять тестовыми способностями из конфигурации. Полноценный интерфейс инвентаря, покупка способностей и сохранение коллекции относятся к последующим фазам.

### **8.2. Цвет способности**

У каждой способности должны быть:

- уникальный `id`;
- название;
- цвет энергии;
- стоимость активации;
- редкость;
- описание;
- параметры эффекта.

Пример структуры:

```
interface AbilityDefinition {
  id: string;
  name: string;
  color: 1 | 2 | 3 | 4;
  rarity: 'common' | 'rare' | 'epic' | 'legendary';
  energyCost: number;
  description: string;
  effectType: string;
  params: Record<string, number>;
}
```

Редкость и стоимость — разные характеристики. Легендарная способность не обязана стоить меньше обычной. Стоимость определяется балансом и силой конкретного эффекта.

### **8.3. Проверка стоимости**

При активации сервер должен проверить:

1. Матч находится в состоянии `playing`.
2. Игрок не заморожен, если активация в таком состоянии запрещена правилами конкретной способности.
3. Указанный слот существует.
4. В слоте установлена способность.
5. Способность разрешена для текущего режима.
6. У игрока достаточно энергии соответствующего цвета.
7. Способность можно применить в текущем состоянии игры.

Если проверка пройдена, сервер списывает энергию и применяет эффект.

Если проверка не пройдена, энергия не списывается.

Клиент не должен самостоятельно определять, достаточно ли энергии для успешного применения. Он может предварительно отключать кнопку для удобства, но окончательное решение принимает сервер.

## **9. Предлагаемый набор первых тестовых способностей**

В архиве уже реализованы автоматические эффекты цветов. Их можно использовать как основу для тестирования новой системы, но активируемые способности должны быть отдельными действиями.

Ниже — предлагаемый тестовый набор для проверки механики. Это не окончательный баланс способностей.

| Цвет    | Тестовая способность | Эффект                                        |
| ------- | -------------------- | --------------------------------------------- |
| Зелёный | Healing              | Восстанавливает здоровье игрока               |
| Синий   | Freeze               | Замораживает соперника на заданное время      |
| Красный | Destroy Cell         | Удаляет заданное количество кубиков соперника |
| Жёлтый  | Joker                | Добавляет джокер в очередь фигур              |

Для каждой способности стоимость должна задаваться отдельно в конфигурации. Конкретные значения стоимости и силы эффекта необходимо считать параметрами баланса, а не зашивать в алгоритм движка.

В будущем можно добавить несколько способностей одного цвета с разной редкостью и разными эффектами.

Например, для красного цвета:

- удаление нескольких отдельных кубиков;
- удаление одной строки;
- удаление всех кубиков выбранного цвета.

Эти варианты не должны требовать изменения базового протокола активации.

## **10. Архитектура применения способностей**

Рекомендую не размещать всю логику способностей непосредственно в `applyPlayerInput()` или `lockPiece()`.

В `engine.ts` следует создать отдельный механизм:

```
activateAbility(
  state: MatchState,
  playerIndex: 0 | 1,
  slotIndex: number
): AbilityActivationResult
```

Внутри он должен:

1. Получить способность из слота игрока.
2. Найти её определение в реестре способностей.
3. Проверить доступность и стоимость.
4. Списать энергию.
5. Применить эффект.
6. Добавить событие в `state.events`.
7. Вернуть результат операции.

Для эффектов желательно использовать отдельные обработчики, например:

```
applyHealAbility(...)
applyFreezeAbility(...)
applyDestroyCellAbility(...)
applyJokerAbility(...)
```

Так новые способности можно будет добавлять без переписывания основного игрового цикла.

### **10.1. Состояние игрока**

В `PlayerState` добавить четыре слота:

```
abilities: AbilitySlots;
```

При создании матча тестовые слоты заполняются заранее заданными `abilityId`, если это предусмотрено тестовой конфигурацией. В противном случае слоты остаются пустыми.

На этом этапе не требуется база данных: состояние слотов существует в рамках текущего матча. Постоянное хранение коллекции игрока относится к следующей фазе проекта.

## **11. WebSocket-протокол**

В `packages/core/src/protocol.ts` добавить клиентскую команду:

```
z.object({
  type: z.literal('activate_ability'),
  slotIndex: z.number().int().min(0).max(3),
  requestId: z.string().min(1).max(64)
})
```

`requestId` нужен для защиты от повторной обработки одной команды при повторной отправке или сетевых проблемах.

В `GameEvent` добавить событие успешной активации:

```
| {
    type: 'ability_activated';
    player: 0 | 1;
    slotIndex: number;
    abilityId: string;
    energyColor: 1 | 2 | 3 | 4;
    energySpent: number;
  }
```

Также предусмотреть событие или ответ с ошибкой активации. Например:

- `ABILITY_NOT_FOUND`;
- `EMPTY_SLOT`;
- `NOT_ENOUGH_ENERGY`;
- `MATCH_NOT_PLAYING`;
- `ABILITY_NOT_AVAILABLE`.

Ошибки должны передаваться без изменения состояния игры.

### **11.1. Серверная обработка**

В `apps/server/src/server.ts` добавить обработку `activate_ability` рядом с существующей обработкой `input`.

Сервер должен брать `playerIndex` из текущего WebSocket-соединения, а не принимать его от клиента.

Команда должна применяться к соответствующему игроку комнаты. Нельзя позволять клиенту активировать способность от имени соперника.

Защита от повторов должна работать на сервере: повторный `requestId` в рамках матча не должен повторно списывать энергию или повторно применять эффект.

### **11.2. Снимок состояния**

В `SnapshotMessage` передавать:

- энергию обоих игроков;
- четыре слота способностей обоих игроков либо данные, необходимые клиенту для отображения их состояния.

В клиентском интерфейсе игроку достаточно получать данные своих способностей и необходимые сведения о сопернике. Не следует передавать клиенту внутренние серверные объекты или доступ к реестру с изменяемым состоянием.

## **12. Существующие эффекты: обязательное правило совместимости**

В текущем `engine.ts` уже работают автоматические эффекты:

- зелёный доминирующий цвет лечит игрока;
- жёлтый добавляет джокеры;
- синий цвет волны замораживает соперника;
- красный цвет волны запускает метеориты.

В фазах 1А и 1Б эти эффекты **не удалять и не отключать**.

Новая система способностей работает отдельно:

- очистка линии продолжает автоматически запускать старые эффекты;
- очистка линии одновременно начисляет энергию;
- игрок может вручную активировать новую способность;
- ручная активация не должна повторно запускать старый автоматический эффект сама по себе.

Это важное разделение. Например, автоматическое лечение за зелёную линию и ручная способность Healing — два разных механизма. Если они оба восстанавливают здоровье, их суммарное влияние на баланс нужно отдельно проверить тестами.

В частности, старый красный эффект в `applyWaveImpact()` удаляет случайные клетки соперника. Новый `Destroy Cell` должен быть самостоятельным эффектом, а не повторным вызовом старого эффекта волны.

## **13. Интерфейс фазы 1Б**

В `apps/web/src/main.ts` добавить панель из четырёх слотов способностей.

Для каждого слота отображать:

- иконку или цвет способности;
- название;
- стоимость энергии;
- доступность активации;
- состояние пустого слота.

При достаточном количестве энергии кнопка активации становится доступной.

При недостаточном количестве энергии кнопка отображается неактивной, а стоимость остаётся видимой.

После нажатия клиент отправляет `activate_ability`. Он не должен самостоятельно менять здоровье, поле, энергию или состояние соперника.

Результат отображается только после получения подтверждённого серверного состояния и соответствующего события.

**Цель:** создать устойчивую внутриигровую экономику и способы монетизации.

### **5.1. Rewarded Ads**

Игрок добровольно смотрит рекламу и получает награду.

Примеры:

- дополнительная попытка против бота;
- удвоение награды за испытание;
- дополнительный сундук или другой ограниченный бонус;
- восстановление попытки.

Каждый тип награды должен иметь ограничения и серверную проверку подтверждения просмотра.

### **5.2. Косметический магазин**

Добавить:

- скины блоков;
- оформление игрового поля;
- эффекты очистки линий;
- эффекты победы;
- оформление профиля;
- аватары.

Косметические предметы не должны давать несправедливое преимущество в PvP.

### **5.3. Battle Pass**

Сезонная система прогрессии:

- бесплатная ветка наград;
- премиальная ветка;
- задания;
- опыт сезона;
- награды за уровни;
- сезонные косметические предметы.

**Результат фазы 5:** появляются рекламные награды, магазин косметики и сезонная система монетизации.

# **20. Технический план по архитектуре проекта**

Все фазы должны развивать существующую архитектуру, а не создавать второй независимый проект.

| Компонент                       | Фазы    | Основная ответственность                          |
| ------------------------------- | ------- | ------------------------------------------------- |
| `packages/core`                 | 1, 3, 4 | Правила игры, энергия, способности, PvP/PvE       |
| `packages/core/src/protocol.ts` | 1–6     | WebSocket-протокол                                |
| `apps/server`                   | 1–6     | Матчи, комнаты, авторизация, экономика, рейтинги  |
| `apps/web`                      | 1–6     | Игровой интерфейс, профиль, магазин, инвентарь    |
| PostgreSQL                      | 2–6     | Аккаунты, прогресс, монеты, коллекции, статистика |
| Redis — при необходимости       | 3–6     | Временное состояние, очереди, масштабирование     |
| Рекламный SDK                   | 5       | Rewarded Ads                                      |
| Платёжная интеграция            | 5       | Премиальные предложения и Battle Pass             |

Не нужно внедрять все эти компоненты сразу. Например, Redis стоит добавлять только при появлении конкретной необходимости в масштабировании или распределённом состоянии.
